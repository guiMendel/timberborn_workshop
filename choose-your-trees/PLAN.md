## Toolchain and dependencies

Use the built-in mod loader and a C# DLL project with references to this installation's game and Unity DLLs. The [official coding guide](https://github.com/mechanistry/timberborn-modding/wiki/Coding-basics) supports manually referencing game assemblies without Unity. A .NET SDK and a compatible managed decompiler are development prerequisites; verify the assembly target framework and Unity API profile before selecting the project target. Do not infer the mod target framework from Harmony's package alone.

Prefer a code-only build with programmatic UI Toolkit elements and native game factories, avoiding an AssetBundle if unnecessary. If those APIs require imported assets or templates, use the official Unity project with editor `6000.5.11f1` and import the installed game's references/assets. Keep project configuration, source, translations, generated output and setup instructions under this folder; reference installed DLLs through a configurable local path and do not commit or distribute them.

Harmony is the proposed runtime dependency for narrow hooks in target choice and the existing priority tool, unless decompilation reveals suitable supported extension points. Reference a compatible Timberborn Harmony release and declare its exact mod ID in the manifest and Workshop required items. Its [maintainer's instructions](https://github.com/eMkaQQ/timberborn-harmony) require both declarations. Verify the installed/released wrapper and architecture compatibility first. Mod Settings is a required runtime dependency for the requested tile/tree lifetime selector; verify its current API, compatible release and exact manifest ID using the [maintainer documentation](https://github.com/eMkaQQ/timberborn-modding#mod-settings), then declare it in the manifest and distribution requirements. TimberUi, Moddable Timberborn and TimberAPI are not currently justified dependencies.

## Implementation sequence and gates

1. **Resolve API contracts before scaffolding.** Decompile the candidate assemblies and inspect official [architecture](https://github.com/mechanistry/timberborn-modding/wiki/Timberborn-architecture) and [UI](https://github.com/mechanistry/timberborn-modding/wiki/User-interface) examples against this build. Record exact target signatures, DI/configurator registration, entity component attachment, persistent entity identity, native priority levels/default and tree identification. Trace `FindCuttable` through range, designation, reservation and pathfinding checks. Trace `BuilderPriorityTool` from rectangle selection through candidate collection, preview and assignment. Exit gate: a documented, minimal hook for each feature and a successful empty-mod load.

2. **Add mode-aware priority storage and Mod Settings configuration.** Register a Mod Settings selector with `Tile` as the default and `Tree` as the alternative. Resolve all reads and writes through one priority service shared by forestry, panel and tool. Use native priority levels/default and namespaced serialization keys. In tile mode, persist a sparse save-scoped map keyed by the verified logical tree tile coordinate (including elevation if the game permits independent tree-bearing surfaces); keep entries after chopping/removal and apply them to later trees at that tile. Do not key tile state by entity ID. In tree mode, store priority on a mod-owned persistent tree component, or a saveable singleton map keyed by the game's persistent entity ID if component restoration is unsuitable; never use Unity instance IDs. Remove tree-owned state on the verified chop/removal event, including cases where chopping retains an entity; a replacement starts normal. Keep both stores independent of `BuilderPrioritizable`, and missing data means normal priority. Preserve priority when cutting designation is toggled. Verify the setting's global/per-save semantics and load order: restoring a save must not silently reinterpret its priority data using an unrelated global selection. When switching modes, convert all active priorities to the new mode while preserving their values: tree priorities become priorities of their tiles, and tile priorities become priorities of the trees occupying them. Resolve and document how to handle prioritized tiles with no tree when switching to tree mode, and whether empty tiles can be assigned priority; a tree-specific value has no tree to attach to in that case. Exit gate: settings default is tile; each mode round-trips correctly; tile state survives replacement, tree state resets after chopping; active priority values survive mode switches.

3. **Implement forestry selection only.** Prefer ordering/filtering candidates at the forestry-specific search boundary, before the native final chooser. Search priority tiers from highest to lowest while preserving all native checks; an unreachable or reserved high-priority tree must allow a lower-priority reachable tree. Within a tier preserve the vanilla chooser and distance/tie behavior. Scope the change to lumberjacking, including bot workers if that path supports them; avoid changing generic yield selection for gatherers and foresters. Keep existing work and reservations until the next normal target acquisition; this avoids cancellation loops. Resolve each candidate through the active mode in the shared priority service. Re-evaluate after priority edits, mode changes and tree/designation changes without caching stale eligibility. Exit gate: higher priority wins when eligible, lower tiers remain usable, equal priorities behave like vanilla, and multiple workers retain valid reservations.

4. **Add the tree panel section.** Register a fragment shown only for verified tree entities. Label it `Lumberjacking`, create the priority row with native factories/styles and tooltips, and route edits through the same mode-aware state setter used by the tool. Refresh the selected value when the active mode changes. Respect fragment initialization/show/update/clear lifecycles and unsubscribe callbacks on selection changes. Add English and Brazilian Portuguese localization keys. Exit gate: panel switching does not modify the previously selected tree or leak callbacks; non-tree panels remain intact.

5. **Extend the existing Assign Priority tool.** Keep the original tool entry, priority levels, construction handling and shortcuts. Add tree candidates to its existing click/rectangle flow and preview/highlighting using a separate tree adapter, rather than making trees construction entities. Apply one selected priority to both applicable construction sites and trees in mixed areas, through their respective setters; tree reads/writes and previews use the active storage mode. Setting priority must never designate a tree for cutting. Verify vertical/area selection semantics and exclude bushes, crops and unrelated entities. Exit gate: click, drag, mixed selections and all construction-only operations retain expected behavior. If native candidate handling cannot be extended safely, record the exact blocker before changing the requested interaction.

6. **Decide chopping progress from evidence.** Trace the work executor and `TreeRemoveYieldStrategy` to identify completed/required chopping work, its owner, reset conditions and save/load representation. `Yield`, growth and dying progress are not proof of chopping progress; stock removal may be discrete. Probe interrupted work, multiple workers, partial log removal and save/reload. Only add a bar if a reliable per-tree measure exists and its lifecycle survives or accurately reconstructs after reload. Render it from authoritative game state; do not persist a UI percentage or infer elapsed time. If work state is genuinely per-tree but not persisted, assess a narrowly scoped persistent representation before promising support. If no truthful measure exists, omit the bar and document that result, as allowed by the requirements. Exit gate: either demonstrated accurate progress across load or an explicit evidence-backed omission.

7. **Package and validate.** Produce a local mod directory containing the verified manifest schema, DLL and any localization/UI resources. Add reproducible build/deploy instructions, compatibility baseline, dependency versions and progress-bar decision. Test after restarting the game with Mod Settings, Harmony if used, and this mod enabled. Publishing is a separate step.

## Acceptance checks

- Controlled map with reachable marked trees: lower-priority nearby versus higher-priority farther away; all priority tiers; equal-priority baseline.
- High-priority trees unmarked, unreachable, out of workplace range, already reserved or otherwise ineligible; native valid lower-priority work still proceeds. Include immature/dead trees according to native eligibility.
- Multiple flags/workers and overlapping ranges; edits during travel/chopping; designation removal; tree destruction/replanting; beaver and bot paths where available. Check that no duplicate reservations, stuck workers or endless reacquisition appear.
- Tree panel row and Assign Priority click/drag give identical state; mixed construction/tree areas work; construction-only behavior and other resource jobs are unchanged.
- Mod Settings selector defaults to tile. In tile mode, priority survives chopping, an empty interval and natural/planted replacement; verify elevation/coordinate semantics. In tree mode, chopped and replaced trees return to normal, including retained-entity lifecycles. Confirm unrelated tiles and trees remain unchanged.
- Switch modes with distinct values in both stores, while a tree is selected and while work is in flight; verify active priority values transfer into the new mode and verify global/per-save setting behavior; cover prioritized tiles with no tree. Both panel and tool must immediately reflect the active mode.
- Save/reload in both modes with default and distinct priorities, tile entries with no current tree, old save without mod data, removed trees and in-flight reservations. If displaying progress, compare immediately before/after load and after interrupted work.
- Both factions, multiple tree species, English/pt-BR UI, large selections and repeated panel switching. Check frame responsiveness, game log exceptions and duplicate hooks after reload.
- Add focused automated tests for priority-tier ordering/default/load compatibility if logic can be isolated; game integration tests remain the authority for reachability, reservations and UI.

Completion means these checks pass on the recorded game build, required dependencies are declared, and any omitted progress bar is explicitly explained. Current status: planning complete; no code, installation or runtime verification performed.
